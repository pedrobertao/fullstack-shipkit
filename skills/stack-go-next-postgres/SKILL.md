# Personal stack: Go (Fiber) + React (Next.js or Vite) + PostgreSQL + Redis + RabbitMQ

This skill describes how the user likes their personal projects to be built. The goal is for every new project to start out like the previous ones, so the user never has to re-explain structure, libraries and conventions in each conversation.

When a choice below conflicts with something the user explicitly asks for in the conversation, follow the user. When something isn't covered here, prefer the simplest solution with the fewest dependencies, and state which choice you made.

## Frontend variant

The backend, database and infra choices below are fixed. The frontend has two supported variants: **Next.js (default)** or **Vite + React Router + TanStack Query**. Resolve which one applies, in order:
1. `CLAUDE.md` already declares one → use it, no need to ask.
2. The user states one in the conversation → use it (and it's the kind of project-wide decision worth adding to `CLAUDE.md`, per `grill-me`'s final-result step, if this is a new project).
3. Neither → default to Next.js without asking; only ask if the user's request signals they're weighing the choice (e.g. mentions Vite, SPA, "no SSR").

Once resolved, read `references/nextjs-frontend.md` or `references/vite-frontend.md` — never both — for the frontend-specific parts of any task below. Everything else in this file and in `go-backend.md`, `auth-jwt.md`, `postgres.md`, `redis-rabbitmq.md` applies unchanged regardless of which frontend variant is in play.

## Principles

- **Simplicity before abstraction.** Three layers (Fiber handler → service → sqlc-generated repository) are enough in most cases.
- **Explicit SQL.** No ORM. Queries live in `.sql` files and the Go code is generated by sqlc, which keeps the SQL readable and type-safe.
- **Postgres is the source of truth.** Redis is cache and ephemeral state (it can be wiped without losing data); RabbitMQ carries asynchronous work. Nothing important lives only in Redis or only in a queue.
- **Slow work leaves the request.** Sending email, processing files, external integrations and anything above ~200 ms go to a RabbitMQ queue and are handled by the worker.
- **Everything runs with one command.** `docker compose up -d` starts Postgres, Redis and RabbitMQ; `make dev` starts the API, worker and frontend.
- **Real TypeScript.** `strict` on, no `any`, API types mirroring the Go DTOs. When creating or changing an endpoint, update both sides in the same response.

## Standard repository layout (monorepo)

```
my-project/
├── backend/
│   ├── cmd/
│   │   ├── api/main.go          # Fiber server
│   │   └── worker/main.go       # RabbitMQ consumers
│   ├── internal/
│   │   ├── config/              # env var loading
│   │   ├── logging/             # builds the *slog.Logger (JSON in prod, text in dev)
│   │   ├── http/                # Fiber app, routes, handlers, middlewares
│   │   ├── auth/                # JWT issuing/validation, password hashing
│   │   ├── service/             # business rules
│   │   ├── cache/               # Redis wrapper
│   │   ├── queue/               # publisher, consumer and message types
│   │   └── db/                  # sqlc-generated code (do not edit)
│   ├── db/
│   │   ├── migrations/          # goose files
│   │   └── queries/             # sqlc queries
│   ├── sqlc.yaml
│   ├── go.mod
│   └── Dockerfile
├── frontend/                    # Next.js (App Router, TypeScript, Tailwind) — shown for the default variant
│   ├── src/app/
│   ├── src/components/
│   ├── src/lib/                 # api.ts, auth.ts, utils.ts (cn)
│   └── src/types/               # types mirroring the Go DTOs
├── docker-compose.yml           # postgres, redis, rabbitmq
├── .env.example
├── Makefile
└── README.md
```

With the Vite variant, `frontend/` follows `references/vite-frontend.md`'s structure instead (`src/routes/`, `src/main.tsx`, no `src/app/`) — everything else in this tree is unchanged.

## Technology choices (defaults)

| Layer | Choice | Why |
|---|---|---|
| HTTP framework | `gofiber/fiber/v2` | User preference; fast, Express-like API |
| Postgres driver | `jackc/pgx/v5` with `pgxpool` | Faster and more complete than `database/sql` |
| Queries | `sqlc` (`sql_package: pgx/v5`) | Plain SQL with typed code |
| Migrations | `pressly/goose` | SQL files with `-- +goose Up/Down` |
| Auth | JWT with `golang-jwt/jwt/v5`: short access token + rotating refresh token | See `references/auth-jwt.md` |
| Passwords | `golang.org/x/crypto/bcrypt` (or argon2id) | |
| Redis | `redis/go-redis/v9` | Cache, refresh tokens, JWT blacklist, rate limiting |
| RabbitMQ | `rabbitmq/amqp091-go` | Official client |
| Logging | `log/slog` (JSON in prod, text in dev), custom request logger with `request_id` | Standard library; same format in API and worker |
| Validation | `go-playground/validator/v10` with `validate:"..."` tags on input DTOs | De facto standard in Go; recommended by the Fiber docs |
| Frontend | Next.js App Router + strict TypeScript (default), or Vite + React Router + TanStack Query | See "Frontend variant" above |
| Styling | Tailwind CSS v4 + `clsx` + `tailwind-merge` — same in both variants | See `references/nextjs-frontend.md` (Tailwind/`cn` section shared by `vite-frontend.md`) |
| Forms | Server Actions when simple (Next) or a plain `useMutation` (Vite); `react-hook-form` + `zod` when complex, either variant | |

## Workflow for a new feature (e.g. "add comments")

Follow this order, because each step depends on the previous one:

1. **Migration** in `backend/db/migrations/` (see `references/postgres.md`). Classify each table by type and run the checklist at the end of that file before delivering.
2. **Queries** in `backend/db/queries/<entity>.sql`; remember to run `make sqlc`.
3. **Service** in `internal/service/` with the business rules. Decide here whether something goes to cache (Redis) or to a queue (RabbitMQ).
4. **Handler + Fiber route** in `internal/http/` (see `references/go-backend.md`), protected by the JWT middleware when login is required.
5. **Message + consumer**, if there is asynchronous work (see `references/redis-rabbitmq.md`).
6. **TypeScript type** in `frontend/src/types/` mirroring the response JSON.
7. **Client function** in `frontend/src/lib/api.ts`.
8. **Page/component** with Tailwind, per the resolved frontend variant (see `references/nextjs-frontend.md` or `references/vite-frontend.md`).

At the end, list the commands the user needs to run (e.g. `make migrate-up && make sqlc`).

## API contract

- Prefix `/api/v1`.
- JSON fields in `snake_case`; in TypeScript keep the same names so no conversion is needed.
- Errors always in this shape:
  ```json
  { "error": { "code": "not_found", "message": "user not found" } }
  ```
- Validation errors (`422`) include the fields, named exactly as in the JSON:
  ```json
  { "error": { "code": "validation", "message": "invalid data",
               "fields": { "email": "must be a valid email", "name": "is required" } } }
  ```
- Paginated lists: `?limit=20&cursor=<id>` and response `{ "items": [...], "next_cursor": "..." }`.
- Dates in RFC 3339 (UTC).
- `401` = missing/invalid/expired token (the frontend tries a refresh); `403` = authenticated but not allowed.

## Assets

`assets/` holds files meant to be copied verbatim rather than retyped. Go source files sit in their own directory per package, mirroring `backend/`'s real layout (`cmd/api/main.go` is `package main`, `internal/config/config.go` is `package config`, `internal/http/validate.go` is `package http`) — Go's actual rule is that every `.go` file in the *same* directory must share one package, so each package gets its own folder here instead of all three sitting flat together. `docker-compose.yml`, `.env.example`, `Makefile` and `Dockerfile` have no package to conflict with, so they stay at the top level. The reference files below say exactly where each one goes.

## What to avoid

- ORMs (GORM, Ent, Prisma).
- Validating input with manual `if`s scattered across the handler; use validator v10 tags and the `bindAndValidate` helper.
- Other loggers (`fmt.Println`, `log`, zap, zerolog, logrus, Fiber's `middleware/logger`); use `slog`. And never log passwords, tokens or cookies.
- `panic` for normal control flow; return an `error` and let Fiber's `ErrorHandler` respond.
- Keeping values from `*fiber.Ctx` (like `c.Params()` or `c.Body()`) after the handler returns without copying them: Fiber reuses its buffers.
- Accessing Postgres, Redis or RabbitMQ directly from the frontend (Next.js or Vite). It talks **only** to the Go API.
- Storing JWTs in `localStorage`; use `HttpOnly` cookies.
- Putting sensitive data in the JWT payload (it is only signed, not encrypted).
- Publishing to a queue inside a transaction and assuming everything worked; see the outbox pattern in `references/redis-rabbitmq.md` when consistency matters.
- Computed results without a unique index (they duplicate on recompute) and CASCADE that deletes history.
- `any` in TypeScript and `SELECT *` in queries.
- Editing files in `internal/db/` by hand (they are generated).
